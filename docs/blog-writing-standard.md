# 博客写作标准

本标准适用于本仓库后续新写或重写的技术博客。以读者能独立理解、实际使用和排查问题为完成条件。

## 组织方式

- 先划定主题和适用范围，建立概念关系，再按职责、阶段或问题层次组织章节。
- 叙述用于说明问题缘由，主体应具有说明书的结构，便于顺序阅读和按问题查阅。
- 不将对话逐条拼接成文章，不以字段清单代替解释，不机械套用固定章节数量。

## 解释一个概念的四个视角

1. 声明者或作者如何表达：语法、字段、结构、输入与约束是什么。
2. 解释者或工具如何理解：谁读取、何时读取、按什么规则处理，哪些环境不支持。
3. 使用者如何使用：怎样调用、配置或操作，得到什么结果。
4. 最终含义：用准确、简洁的定义收束，说明它与相邻概念的边界。

四个视角应自然进入正文，不必给每个小节机械重复四个标题。涉及多个工具、角色或环境时，交代视角变化，并用同一示例比较实际差异。

## 内容应能独立读懂

- 关键术语、缩写和前置知识在首次需要时解释，不用超链接替代解释。
- 说明规则的作用对象、优先级、默认行为、失败情况和适用条件，避免把工具约定写成通用规则。
- 对易混淆概念明确区分，例如声明与执行、安装与解析、类型与运行时、构建与发布。
- 参考链接用于核对来源和进一步阅读。读者不打开它们，也应能理解本文承诺覆盖的内容。
- 自包含不等于穷举生态所有细节；与主题无关的分支不展开，但不能省略理解核心行为必需的环节。

## 示例与验证

- 从最小完整示例建立概念，再通过真实项目说明复杂情况。
- 标明完整文件、局部片段、占位名称、运行位置和所需条件；不能把示意片段说成可直接运行的程序。
- 重要行为给出输入、处理过程和输出，必要时补目录结构、对照表、流程或故障排查表。
- 对影响结论的入口、优先级、版本和环境差异核对证据。可运行的关键示例尽量实际验证。
- 分清源码声明、构建产物、已发布包与线上行为；未验证的内容不能写成已经验证。

## 语言与审阅

- 使用自然、具体的中文，避免夸张评价、空泛总结、反复加粗、模板式过渡和刻意营造的个人经历。
- 不虚构作者实践或判断；保留真实问题与有用的推理过程。
- 完稿后检查：层次是否清楚、术语是否有解释、不同视角是否贯通、定义是否准确、示例是否完整、是否存在理解必须依赖的外链。
- 新文章先保留草稿并交用户审阅，用户明确确认正文与发布后，再提交并部署；单次发布授权不自动延续到下一篇。
